## 2. Базовые принципы

Код должен быть **чистым, читаемым и поддерживаемым** одиночным разработчиком через год после написания. Все принципы ниже — не рекомендация, а обязательство.

### 2.1 SOLID

- **S — Single Responsibility.** Каждый модуль, класс, функция решает **ровно одну задачу**. Если при описании функции приходится использовать «и», «а также», «плюс» — это две функции.
- **O — Open/Closed.** Новая логика добавляется через новые классы/стратегии, а не правкой существующих. Провайдеры доставки, платёжные шлюзы, парсеры, нормализаторы — расширяются новыми адаптерами, не модификацией ядра.
- **L — Liskov Substitution.** Подтипы не ослабляют контракт родителя. Если `Fetcher.fetch()` возвращает `list[RawItem]`, подкласс не возвращает `None` и не кидает неожиданных исключений.
- **I — Interface Segregation.** Не делать «толстых» интерфейсов. Лучше два узких протокола, чем один `PipelineStep` на все случаи.
- **D — Dependency Inversion.** `app/domain/` зависит **от абстракций** (Protocol / ABC, callable-зависимости), а не от конкретных реализаций из `app/crud/`. Доступ к данным инжектится снаружи — так `domain/` тестируется без БД.

### 2.2 KISS

Самое простое решение, которое работает — правильное. Не вводить абстракцию, пока не появилась **вторая** реализация. Три похожих строчки лучше преждевременной метапрограммной магии.

### 2.3 DRY (с оговоркой)

Дублирование устраняется, когда две копии кода действительно описывают **одну и ту же бизнес-концепцию**. Случайное совпадение сигнатур — не повод для общей абстракции (см. правило «Rule of Three»: абстрагируем с третьего повтора).

### 2.4 YAGNI

Не писать код «на будущее». Не делать флагов фич, шимов обратной совместимости, расширяемости под гипотетические требования. Требуется — добавим тогда; YAGNI важнее, чем гибкость «про запас».

### 2.5 Composition over Inheritance

Наследование — только для моделирования «is-a». Переиспользование поведения — через композицию и инъекцию зависимостей. Глубина наследования > 2 — повод остановиться и пересмотреть.

### 2.6 Fail Fast

Ошибки в невалидных данных падают как можно раньше (на границе — в Pydantic-схеме, в валидаторе входных данных). Внутри бизнес-логики доверяем типам.

## 3. Структура проекта и границы ответственности

Проект — **одно FastAPI-приложение** в `app/`. Никаких `apps/`+`packages/`: для соло-разработки плоская структура проще.

Ключевой принцип: **админка — это не отдельное приложение, а набор дополнительных роутов/схем/CRUD с повышенными правами**. Чтобы не мешать публичное и админское, в каждом слое, где это имеет смысл, есть симметричное деление `public/` ↔ `admin/`.

### URL-схема

- `/`, `/login`, `/register`, … — публичный HTML.
- `/admin`, `/admin/users`, `/admin/audit` — админский HTML (требует авторизации).
- `/api/public/v1/...` — публичный JSON API.
- `/api/admin/v1/...` — админский JSON API (требует авторизации).
- `/docs` — Swagger, `/health` — проверка живости.

URL и файловая раскладка совпадают: `api/public/v1/endpoints/<entity>.py` ↔ `/api/public/v1/<entities>`, `web/admin/pages/users.py` ↔ `/admin/users`.

Python-пакеты содержат `__init__.py`, пустые директории — `.gitkeep`. Конкретные модули (`routers.py`, `main.py` воркера, формы админки и т.п.) создаются по мере появления первой функциональности — не заранее.

### 3.1 Зависимости между модулями

Правила строгие, ломать — только с ADR:

- **`api/`, `web/`** — транспортный слой. Роут → вызов функции из `domain/` или `crud/` → рендер/сериализация. **Бизнес-логики в роутах нет.** Внутри каждого транспорта — симметрия `public/` ↔ `admin/`.
- **`domain/`** — чистая бизнес-логика, **общая для public и admin**. **Не импортирует** `app.crud`, FastAPI, Jinja, SQLAlchemy-сессии. **`app.models` импортировать можно**, но с оговоркой: для плоских моделей (без relationships / lazy-load) — без проблем; как только у модели появляются связи, которые читаются лениво, — на границе `domain/` переходим на Pydantic-DTO, чтобы не прятать скрытые SELECT-ы внутри «чистых» функций. Если нужна БД — принимает данные аргументом или зовёт callable-зависимость, переданную извне.
- **`crud/`** — доступ к БД, разделён на `public/` и `admin/`. В `crud/admin/` попадают только операции, которых нет в `crud/public/` (bulk, soft-delete, восстановление, админские фильтры). Обычные операции (`get_by_id`, `list`) — один раз, в `crud/public/`, и переиспользуются админкой.
- **`models/`** — только SQLAlchemy-модели, **одни на обе стороны** (одна таблица — одна модель). Никакой бизнес-логики в методах моделей.
- **`schemas/`** — Pydantic, разделены на `public/v{N}/` и `admin/v{N}/`. Если одна схема нужна обеим сторонам — она в `public/`, admin её импортирует.
- **`core/`** — инфраструктура. `core/admin/` — общие для админки вещи: `require_admin`, `require_role`, `record_action`. Остальное `core/` — от stdlib и внешних библиотек.
- **`workers/`** — вызывает `domain/` и `crud/`, как и `api/`/`web/`. Воркер — ещё один транспорт, не место для логики. Без деления public/admin.
- **`templates/`** — только разметка и макросы. Разделены на `public/` и `admin/`, у каждого свой `base.html`. Никакой логики сложнее `{% if %}` / `{% for %}`. Вычисления (`has_discount`, форматирование цены/даты) — в Python, шаблон получает готовое значение.

**Правило «параллельности транспортов».** Любая фича, реализованная для `web/public/`, должна быть реализуема для `api/public/` без изменения `domain/` и `crud/`. Если добавляя HTML-страницу, ты тянешь бизнес-логику в роут или шаблон — это блокер. Это гарантирует, что в будущем переход на SPA = новый фронт + недостающие эндпоинты в `api/public/`, а не переписывание ядра.

### 3.2 Форма функций в `domain/`

`domain/` — это бизнес-правила, вытащенные из роутов. Требования:

1. **Одна функция — одно действие**: `calculate_cart_total`, `normalize_specs`, `ensure_role_change_allowed`.
2. Принимает и возвращает Pydantic / dataclass / ORM-модель. ORM допустим для плоских моделей без ленивых связей; как только у модели появляются lazy-load relationships, которые функция трогает, — на выходе переходим на Pydantic-DTO, чтобы скрытый SELECT не прятался внутри «чистой» функции.
3. Зависимости (callable для доступа к данным, часы, rng) — через аргументы, не через глобальные импорты.
4. Не логирует HTTP, не знает про статус-коды. Ошибки — через доменные исключения (см. §4.6).
5. Не открывает сессии БД, не коммитит транзакции. Этим управляет вызывающий роут/задача.

### 3.3 Форма роутов

- Роут ≤ 15 строк: зависимости → вызов `domain`/`crud` → ответ.
- Pydantic-схемы запросов/ответов — в `schemas/public/v{N}/` или `schemas/admin/v{N}/`, по стороне.
- HTML-страницы — через `render()` из `web/templates.py` (он выдаёт CSRF-токен и тост), макросы из `templates/public/macros/` или `templates/admin/macros/`.
- HTMX-фрагменты — отдельные роуты в `web/<side>/partials/`, возвращают шаблоны из `templates/<side>/partials/`.
- Маппинг доменных исключений → HTTP-коды — в FastAPI exception handler на уровне приложения (`core/exception_handlers.py`), не в каждом роуте. Сайт получает страницу ошибки (для HTMX — тост), `/api/` — JSON.
- **Админские роуты защищаются на уровне роутера**, а не в теле: `APIRouter(..., dependencies=[Depends(require_admin)])`. Это и у `api/admin/`, и у `web/admin/`.
- **Изменяющие web-формы защищены CSRF** на уровне роутера: `APIRouter(dependencies=[Depends(csrf_validate)])`. Токен — скрытое поле `token_key` в форме или заголовок `X-CSRF-Token` (HTMX ставит его сам, `static/js/csrf.js`).

## 4. Правила для функций, классов, методов

### 4.1 Размеры (ориентиры, не догма)

- **Функция** ≤ 20 строк тела. Если больше — почти наверняка делает две вещи.
- **Класс** ≤ 200 строк. Если больше — почти наверняка нарушает SRP.
- **Количество аргументов функции** ≤ 4. Больше — группировать в dataclass/Pydantic-модель.
- **Вложенность** ≤ 3 уровня (`if` внутри `for` внутри `try` — предел). Глубже — выделять функцию или применять early return.

### 4.2 Единая ответственность

Функция делает **одно**: или считает, или читает, или пишет, или трансформирует, или оркестрирует. Не всё сразу.

- ❌ `get_and_normalize_and_save(item)` — три глагола.
- ✅ `fetch_item` + `normalize_item` + `save_item` — оркестрируются в use-case.

### 4.3 Команды vs Запросы (CQS)

Метод либо **меняет состояние** (command, возвращает `None` или минимум данных), либо **возвращает данные** (query, ничего не меняет). Не смешивать.

### 4.4 Чистота

Доменные функции в `app/domain/` по умолчанию — **чистые**: без I/O, без глобального состояния, без времени и рандома. Если нужны — инжектятся как зависимости (`clock: Clock`, `rng: Random`), чтобы тестировать.

### 4.5 Именование

- Функции — **глагол**: `create_order`, `render_table`, `normalize_unit`.
- Булевы — **предикат**: `is_published`, `has_discount`, `can_be_deleted`.
- Классы — **существительное**: `OrderCalculator`, `SpecNormalizer`.
- Протоколы/интерфейсы — без префикса `I`: `ItemRepository`, а не `IItemRepository`.
- Переменные — **полные слова**, не аббревиатуры: `item_id`, не `iid`; `category`, не `cat`.
- Приватные — с `_`: `_build_query`, `_cached_schema`.

### 4.6 Исключения

- Пользовательские исключения — **свои классы** в `errors.py` своего сабдомена: `app/domain/admin/errors.py`, `app/domain/<субдомен>/errors.py`. Базовый `DomainError` и общие `NotFoundError`, `ConflictError`, `PermissionDeniedError`, `ValidationError`, `RateLimitedError`, `UpstreamError` — в `app/domain/errors.py`, от них наследуются все доменные исключения. HTTP-код выводится из базового класса.
- Не ловим `Exception` широко. Ловим конкретные.
- Не используем исключения для потока управления.
- На границе HTTP — маппинг доменных исключений в HTTP-коды через FastAPI exception handlers, не `try/except` в роутах.

## 5. Типизация

- **Строгий режим тайпчекера** для `app/domain/` и `app/crud/`.
- Все публичные функции аннотированы полностью (аргументы + возврат).
- `Any` — запрещено без явного `# type: ignore[...]` с комментарием-причиной.
- `Optional[X]` только когда `None` — осмысленное значение. Для «ещё не загружено» использовать отдельные состояния.
- Доменные типы — через `NewType` или dataclasses, а не голые `str`/`int` (`ItemId = NewType("ItemId", int)`).

## 6. Комментарии и документация

По умолчанию **не пишем комментарии**. Хорошие имена заменяют комментарии.

Пишем комментарий, только если:

- объясняет **почему**, а не **что** (скрытый инвариант, неочевидное бизнес-правило, обход бага библиотеки);
- содержит ссылку на внешнюю спеку / issue / ADR;
- `TODO(имя, дата)` — с автором и датой, иначе не оставлять.

**Запрещено:**

- Комментарии вида «# increment i by 1», «# get user».
- Docstrings, повторяющие сигнатуру.
- Комментарии-артефакты от удалённого кода («# removed», «# was: ...»).
- Отсылки к текущей задаче / фиче внутри кода — это для сообщения коммита.

Docstrings пишем для:

- публичных функций `app/domain/`;
- нетривиальных алгоритмов (расчёты, нормализация, матчинг);
- публичных классов-сервисов.

Формат docstring — короткий, одно-двухстрочный. Многоабзацные docstrings — запрещены.

## 7. Ошибки и логирование

- Логи — JSON через `python-json-logger` (`app/core/logs/config.py`), в stdout. Один логгер на модуль: `logger = logging.getLogger(__name__)`.
- У каждого запроса есть `request_id` (`core/middleware/request_id.py`): он в заголовке ответа `x-request-id`, в access-логе и в записи о необработанной ошибке. Жалоба со скриншотом → точка в логе.
- Не логируем в `domain/` инфраструктурные события (HTTP-статусы и т.п.). Логирование уровня запроса — в `app/core/middleware/`.
- Не логируем пароли, токены, платёжные данные, полные тела запросов с PII.
- Ошибки, которые должны приводить к алерту — идут в Sentry (когда подключим); остальное — в обычный лог.

## 8. Работа с БД

- Доступ к БД — **только через `app/crud/`**. Прямые запросы SQLAlchemy в `app/web/`, `app/api/`, `app/domain/` — запрещены.
- В тестах `domain/` слой `crud/` подменяется in-memory-реализацией через DI, без хождения в Postgres.
- Один CRUD-модуль — одна агрегатная сущность (`crud/public/<entity>.py`). Не городить `GodCRUD`.
- **Фильтры в базовый CRUD передаются словарём вторым аргументом**, а не именованными: `crud.get(session, {'id': 1})`, не `crud.get(session, id=1)`. Именованными остаются только `order_by`, `limit`, `offset`, `_detail`, `defaults`. Полный список методов — в [app/crud/crud_methods_description.md](app/crud/crud_methods_description.md).
- Для сложных условий (OR, LIKE, диапазоны) — методы `*_by_condition`, принимающие SQLAlchemy-выражения.
- **Мягкое удаление** (`soft_delete*`, `restore`, `get_with_deleted`) — для сущностей, которые нужно уметь восстановить. Требует полей `is_deleted` / `deleted_at` в модели. Обычные `get*` про флаг не знают и вернут помеченные записи — фильтр передаётся явно: `crud.get_multi(session, {'is_deleted': False})`. Если в публичной выдаче удалённых быть не должно, фильтр ставится в CRUD-подклассе сущности, а не в каждом роуте.
- Транзакции управляются на уровне роута или фоновой задачи, не внутри CRUD-функций.
- **Сессии БД — только через FastAPI `Depends(get_async_session)`**, не создавать движок/сессию внутри роутов, use-case-ов, CRUD-функций. Сегодня отдаётся одна сессия; завтра при появлении read-реплики — две (`get_write_session`, `get_read_session`). Код, получающий сессию через DI, не меняется.
- Миграции — **только Alembic**, никаких `Base.metadata.create_all()` в рантайме, кроме тестов. Пишет их `--autogenerate` из моделей, а не рука (§8.2).
- JSONB-поля — читаются и пишутся через Pydantic-схемы, а не как сырой `dict`.
- **Уникальность — на уровне БД** (`UNIQUE INDEX`), не через `SELECT ... → INSERT`. При конкурентных запросах это race condition; ловим `IntegrityError` и возвращаем доменную ошибку.

### 8.1 Стиль моделей SQLAlchemy

Только **SQLAlchemy 2.0 declarative**: `Mapped[...]` + `mapped_column(...)`. Легаси `Column(...)` и старый `declarative_base()` — запрещены.

Все `relationship(...)` — **двусторонние, через `back_populates`**. `backref` не использовать: обе стороны связи должны быть явно описаны в обоих классах. Это даёт явную типизацию через `Mapped[list["Child"]]`, корректно работает со строгим тайпчекером и делает модели читаемыми по одной стороне.

Правила:

- В начале файла — `from __future__ import annotations`. Это делает все аннотации строковыми (PEP 563), убирает необходимость экранировать forward-reference и работает корректно с `TYPE_CHECKING`.
- Импорты других моделей, нужные **только для аннотаций**, заворачиваются в `if TYPE_CHECKING:` — так не будет циклических импортов на этапе загрузки модулей.
- Обязательная аннотация `Mapped[...]` у каждого атрибута (колонки и relationship).
- Nullable выводится из типа: `Mapped[int]` — `NOT NULL`, `Mapped[int | None]` — nullable.
- Для коллекций — `Mapped[list[Child]]` (без кавычек — их делает ненужными `from __future__ import annotations`).
- FK-колонка и `relationship` описываются рядом: сначала `*_id`, потом связь.
- `__tablename__` — **автоматически** из `app/models/_base.py`: CamelCase → snake_case, в единственном числе (`Category → category`, `ItemImage → item_image`). Вручную указывается только для экзотических случаев или при переопределении имени от сторонней библиотеки (`User` от fastapi-users — `user`).
- Имена индексов и констрейнтов — из `naming_convention` в `_base.py`, руками не задаются.
- Колонкам — `comment='...'` по-русски: его видно в DBeaver, и схема читается без кода.
- Enum модели лежит в том же файле, что и модель. Если enum используется в **≥2 моделях** — выносится в `app/models/enums.py`.
- Общие колонки — миксинами из `app/models/mixin/`: `IntIdPkMixin`, `CreatedAtMixin`, `UpdatedAtMixin`.
- **Новая модель — импорт в `app/models/__init__.py` и `app/core/base.py`**, иначе автоген её не увидит.

Пример:

```python
from __future__ import annotations

from typing import TYPE_CHECKING

from sqlalchemy.orm import Mapped, mapped_column, relationship

from app.models._base import Base
from app.models.mixin.int_id_pk import IntIdPkMixin

if TYPE_CHECKING:
    from app.models.item import Item


class Category(Base, IntIdPkMixin):
    name: Mapped[str] = mapped_column(comment='Название')

    items: Mapped[list[Item]] = relationship(back_populates='category')


# item.py
class Item(Base, IntIdPkMixin):
    category_id: Mapped[int] = mapped_column(ForeignKey('category.id'))
    category: Mapped[Category] = relationship(back_populates='items')
```

### 8.2 Схему описывают модели, а не миграции

**Источник истины о схеме — `app/models/`. Миграция — производная, её пишет `--autogenerate`.**

Всё, что попадает в схему, объявляется в модели: колонки, типы, `nullable`, `server_default`, `UNIQUE`, `CHECK`, **индексы** (`index=True` для одноколоночных, `Index(...)` в `__table_args__` для составных и частичных), `ondelete`/`onupdate` у внешних ключей, значения enum. Руками в миграции дописывается только то, чего автоген в принципе не умеет (см. ниже), — и тогда то же самое **обязано** появиться в модели.

Причина не в аккуратности, а в том, что созданное мимо моделей живёт ровно до следующего сквоша. Автоген сравнивает БД с `Base.metadata`; объекта, которого в метаданных нет, для него не существует. При пересборке миграций он молча исчезнет — без ошибки, без предупреждения, без падения тестов. Так в одном из прошлых проектов терялись индексы, созданные `op.create_index` и не объявленные в моделях. Запросы после такой потери не ломаются, а переходят на seq scan: деградация видна не в CI, а на проде под нагрузкой.

Порядок работы:

1. Правим модель в `app/models/`.
2. `make revision m="..."` (= `alembic revision --autogenerate -m "..."`).
3. **Читаем сгенерированный файл глазами.** Автоген — черновик, а не оракул: он пропускает переименования (видит их как drop + create с потерей данных), смену типа с несовместимым `USING`, изменения `CHECK` и частичных индексов.
4. Правим миграцию, если нужно, — но правкой данных и порядка операций, а не добавлением объектов схемы мимо моделей.
5. `make migrate`, затем `uv run alembic check` — расхождений моделей и БД быть не должно.

**Что автоген не умеет — и как с этим быть:**

| Случай | Решение |
|---|---|
| Новое значение в enum (`ALTER TYPE ... ADD VALUE`) | Добавить в enum в модели — при сквоше растворится само; в инкрементальной миграции дописать `op.execute` руками |
| Миграция данных (`UPDATE`, backfill, перенос между таблицами) | Только руками в миграции. Схемы не касается — терять нечего |
| Переименование колонки/таблицы | Заменить `drop_column` + `add_column` на `op.alter_column(new_column_name=...)` |
| Backfill перед `NOT NULL` | Добавить колонку nullable → `UPDATE` → `alter_column(nullable=False)` |
| Расширения, триггеры, функции, materialized view | `op.execute` в миграции. В метаданные не попадают — **записать в ADR**, иначе при сквоше исчезнут беззвучно |

**Проверка перед сквошем миграций:** собрать две базы — одну прогоном всей цепочки, другую автогеном из моделей — и сравнить схемы (колонки, индексы, констрейнты, enum). Разница означает, что что-то живёт только в миграциях. Расхождение в порядке значений enum — допустимо, на работу не влияет.

Если правило применить не получается — объект в метаданных не выражается, автоген его теряет — **остановиться и обсудить** (§13), а не оставлять расхождение молча.

## 9. HTTP-слой (`app/api/`, `app/web/`)

- Роут — ≤ 15 строк: парсинг зависимостей → вызов функции из `domain/` или `crud/` → рендер/сериализация.
- Pydantic-схемы запросов/ответов — в `app/schemas/<side>/v{N}/`, где `<side>` — `public` или `admin`.
- Зависимости FastAPI (`Depends`) — для инъекции сессий БД, текущего пользователя, шаблонизатора.
- Валидация входа — Pydantic, не ручные `if`.
- Рендер шаблонов — через `render()`; логика внутри Jinja — минимальна (макросы для повторяющихся блоков).
- Ответ на успешную отправку обычной формы — редирект (`redirect` / `redirect_with_toast` из `web/`), а не страница: иначе F5 отправит форму повторно. Ошибку ввода показываем той же страницей с введёнными данными и `toast_context(...)` — редирект стёр бы введённое.

### 9.1 Именование Pydantic-схем

- **API-схемы (DTO запросов/ответов)** — с суффиксом `Schema`: `ItemSchema`, `ItemCreateSchema`, `ItemUpdateSchema`. Суффикс снимает коллизию с ORM-моделями (`Item` в `app/models/` — SQLAlchemy, `ItemSchema` в `app/schemas/` — Pydantic).
- **Админские формы** (ввод HTML-формы, не API-DTO) — с суффиксом `Form`: `ItemCreateForm`, `ItemEditForm`, `ItemBulkDeleteForm`. Форма отражает назначение (валидация ввода HTML-формы), а не сериализатор ответа.
- ORM-модели и enum — **без суффикса** в классах (`Item`, а не `ItemModel`). Исключение, унаследованное из прошлых проектов: enum-ы ролей и статусов с суффиксом `Enum` (`UserRoleEnum`) — так их не путают с одноимёнными полями.

### 9.2 Реактивность: правка видна сразу, без перезагрузки

**Изменил данные через HTMX — обнови на странице всё, что их показывает.** Не только блок, где была форма: шапку, счётчики, соседние вкладки, списки выбора в других формах. Иначе страница показывает старое, пока её не перезагрузят.

- Правленый блок меняется обычным swap-ом (`hx-target`). Остальные блоки досылаются **out-of-band** (`hx-swap-oob`) в том же ответе. Отдельный запрос за каждым блоком не нужен.
- Если на странице много зависимых блоков — заводится один partial-сборщик oob-блоков страницы, который роут включает флагами. Новый зависимый блок — это новый флаг там же, а не своя досылка в роуте.
- Блок, который досылается oob-ом, живёт в **отдельном partial** с `{% if oob %} hx-swap-oob="outerHTML"{% endif %}`. Его разметка не дублируется. Контекст для него собирает общая функция, а не копия в каждом роуте.
- **Досылать блок можно, только если он есть на странице.** Если цели нет, HTMX выдаст `oobErrorNoTarget`. Тот же роут, вызванный с другой страницы, не должен досылать блоки, которых там нет.
- **Partial, который сам включает сборщик oob-блоков, нельзя досылать через этот же сборщик.** Шаблоны зациклятся. Досылаемую часть выносим в отдельный partial.
- Добавляя форму, спроси себя: **где ещё на этой странице видны данные, которые она меняет?** Каждое такое место обновляется в ответе.
- Проверка — в браузере: сделать правку и убедиться, что всё зависимое обновилось **без перезагрузки**.

Где не применимо:

- **Отправка без JS** (обычный POST) отвечает редиректом, и страница собирается заново. Досылать нечего.
- **Чужие правки не догоняем.** Если данные поменял другой пользователь, страница узнает об этом при следующей загрузке. Websocket-ов и поллинга ради этого не заводим (YAGNI).
- **Переход на другую страницу** после действия (создание, вход) — это обычный редирект, а не oob.

### 9.3 Никаких браузерных диалогов

**`alert()`, `confirm()`, `prompt()` и `hx-confirm` на сайте запрещены**, и в публичной части, и в админке. Системное окно браузера выглядит чужим, на телефоне выглядит по-разному в разных браузерах, и его не оформить под сайт. `hx-confirm` — это тот же `confirm()`.

- **Подтверждение действия** (удаление, необратимый шаг) — наше окно: макрос `confirm_dialog` из `templates/public/macros/modal.html` (`x-data="{ confirming: false }"`, кнопка `type="button"` открывает окно, внутри `modal-backdrop` → `modal-panel` → «Отмена» и `btn-danger`). Закрывается по Escape и клику по подложке.
- **Сообщение об итоге** — тост (`static/js/toasts.js`): `window.toast(...)`, `HX-Trigger` из ответа (`attach_toast`) или `?toast=` после редиректа (`redirect_with_toast`).
- **Ошибка в HTMX-запросе** приходит тостом, а не фрагментом: `web/errors.py` отвечает 200 с пустым телом и `HX-Trigger`, чтобы не затереть обновляемый блок.

### 9.4 Фронтенд-стек

- **HTMX** — всё, что требует данных с сервера. Никаких ручных `fetch` + `innerHTML`. HTMX-эндпоинт возвращает HTML-фрагмент, не JSON.
- **Alpine.js** — только локальная интерактивность (открыть/закрыть, табы). Состояние сервера в Alpine не дублируется.
- **Tailwind CSS v4** — стили классами в шаблонах, без `style="..."`. Цвета — только токенами из `@theme` в `tailwind/input.css`. Повторяющийся ≥ 3 раз блок — компонент в `@layer components`.
- HTMX и Alpine лежат локально в `static/js/`, не с CDN. Подключение статики — с `?v={{ static_version('...') }}`, чтобы обновление не застревало в кэше браузера.
- Tailwind-бинарь скачивается `make tailwind`, Node в проекте нет. CSS собирается `make css`, в Docker — на этапе сборки образа.

## 10. Админка (встроена в приложение, не отдельный модуль)

Админка — **не отдельное приложение**, а дополнительные роуты/схемы/CRUD с повышенными правами. Во всех слоях, где это имеет смысл, живёт симметричным деревом `public/` ↔ `admin/`:

- Роуты — `app/api/admin/v1/`, `app/web/admin/`.
- Шаблоны — `app/templates/admin/` (свой `base.html`, своя навигация).
- Схемы — `app/schemas/admin/v{N}/`.
- CRUD — `app/crud/admin/` (только то, чего нет в `crud/public/`).
- Общие зависимости (`require_admin`, `require_role`, `record_action`) — `app/core/admin/`.

### 10.1 Что принадлежит админке

Админскими считаются операции, которые:

- **Меняют состояние** в обход обычного пользовательского потока (bulk-правки, принудительная публикация, модерация, восстановление удалённого).
- **Видят то, чего не видит публичный API** (мягко удалённые записи, черновики, аудит-лог, очередь модерации, статус фоновых задач).
- **Существуют только в админке** — дашборд, импорт CSV/JSON, управление ролями.

### 10.2 Права доступа

- **Авторизация — общая, из `app/core/auth/`**. Отдельного механизма входа в админку нет. Текущий пользователь — через зависимости из `app/core/auth/users.py` (API) и `app/web/dependencies.py` (сайт).
- Корневой admin-роутер (и `api/admin/v1/`, и `web/admin/`) имеет зависимость прав на уровне роутера. Авторизация не дублируется в каждом эндпоинте.
- Права уровня действия — через `Depends(require_role(...))` из `app/core/admin/permissions.py`. Никаких `if user.role == ...` в теле роутов.
- Модели пользователя/роли — в общем `app/models/`, не дублируются для админки.

### 10.3 Что НЕ дублируется между public и admin

- **`domain/`** — общий. Одни и те же функции вызываются с обеих сторон.
- **`models/`** — общие. Одна таблица — одна модель.
- **Операции чтения** — если `crud/public/<entity>.py` уже умеет `get`, админка его импортирует, а не пишет свой.
- **Схема ответа** — если DTO одинаковый, он в `schemas/public/v1/` и используется обеими сторонами.

### 10.4 Формы админки

- Форма админки — Pydantic-модель в `app/schemas/admin/v{N}/<entity>.py` (`ItemEditForm`, `ItemCreateForm`).
- Форма отвечает только за валидацию ввода. Сохранение — через вызов функции из `domain/` или `crud/`, не через метод формы.
- HTMX-валидация полей — отдельный роут в `web/admin/partials/`, возвращает фрагмент с ошибкой/подсветкой.

### 10.5 Аудит изменений

- Все изменяющие admin-действия пишутся в `audit_log` (кто, что, когда, детали): `record_action(...)` из `app/core/admin/audit.py`, в той же сессии и том же коммите, что и само действие.
- Новое действие — новое значение `AuditActionEnum` (и `op.execute('ALTER TYPE ... ADD VALUE ...')` в миграции, §8.2).

### 10.6 Длинные операции

- Bulk-операции, импорты, экспорты, массовая перестройка — **через очередь задач**, не синхронно в роуте. Роут ставит задачу и сразу возвращает «запущено».
- Прогресс — через отдельный HTMX-роут в `web/admin/partials/`, который читает статус задачи из Redis.

### 10.7 Что НЕ делать

- **Не писать в БД в обход `domain/`-валидации.** Даже «просто поправить поле» — через use-case, чтобы те же правила работали в импортерах, публичном API и админке.
- **Не дублировать чтение в `crud/admin/` тем, что уже есть в `crud/public/`.** Если операция одинаковая — она одна, в `crud/public/`.
- **Не подключать готовые админки** (SQLAdmin, Starlette-Admin) там, где есть кастомная бизнес-логика форм и модерации — они будут мешать.
- **Не строить свой «AdminBaseView» с магией на старте.** Копипаста → выделение общего после третьего повтора (rule of three).

## 11. Тесты

### 11.1 На MVP тесты не пишем

**Пока идёт MVP, новые тесты не пишутся.** Код меняется быстрее, чем окупается их поддержка: проверяем гипотезу, а не стабилизируем API. Ручной проверки через Swagger и браузер достаточно.

Не пишем: тесты роутов, CRUD, схем, интеграционные тесты, тесты вёрстки.

**Исключение — правила, ошибка в которых не падает и не видна глазами**: видимость данных, права доступа, деньги. Ошибка там молча открывает закрытое или считает неверно — это утечка или убыток, а не сломанная кнопка. Тесты там чистые, без БД, прогон — секунды (образец — `tests/domain/admin/test_roles.py`). _TODO: перечислить такие места проекта._

Написанное в `tests/` не удаляем: оно есть не просит. Тесты каркаса (`tests/crud/`, `tests/api/`) остаются как есть.

К остальному покрытию возвращаемся после проверки продуктовой гипотезы — тогда работают правила §11.3.

### 11.2 Когда запускать тесты

**Не запускать весь `pytest` без нужды.** Полный прогон поднимает Postgres и занимает время — это трата времени и токенов.

- Запускать **только то, что покрывает затронутый функционал**: тронул `domain/admin/` — `make test p=tests/domain/`.
- Правка не затрагивает покрытый тестами код (документация, шаблоны, конфиги, новые эндпоинты) — тесты не запускать вообще.
- Полный прогон — только по явной просьбе или перед релизом.
- Ruff и тайпчекер — дёшевы, запускать всегда (`make lint`).

### 11.3 Правила на после MVP

Действуют, когда гипотеза проверена и продукт стабилизируется:

- Unit-тесты для `app/domain/` — **без БД, без сети**. Зависимости от `crud/` мокаются через DI.
- Интеграционные тесты — в `tests/`, с реальным Postgres (отдельная база из `.env.test`), не с моком.
- Один тест проверяет **один сценарий**. Имя теста — описывает поведение: `test_create_order_applies_discount_for_bulk_quantity`.
- `pytest` фикстуры — для setup, не для логики теста.
- Покрытие — цель не в процентах. Обязательно покрыты: use-cases в `domain/`, расчёты (цены, скидки, рейтинги), валидация схем, авторизация.

## 13. Git и коммиты

- Сообщения коммитов — **на английском**, повелительное наклонение: «add category fixture», не «added category fixture».
- Один коммит — одна логическая правка. Не мешать рефакторинг с новой фичей.
- **Коммитим прямо в `main`.** Разработчик один, ревьюить некому — ветка и PR добавляют шаг, но ничего не проверяют. Отдельная ветка заводится только под то, что нельзя оставить в `main` посреди работы: долгий рискованный рефакторинг, эксперимент, который может не взлететь.
- Раз ветки нет, всё держится на коммите: **`main` не оставляем сломанным**. Каждый коммит самодостаточен — Ruff и тайпчекер проходят, приложение поднимается. **Пуш в `main` — это деплой** (§20).
- **Если во время реализации фичи нужен рефакторинг или изменение архитектуры/структуры, чтобы решить задачу без костыля — остановиться и спросить.** Коротко описать: что хочется тронуть за пределами самой фичи, почему иначе будет костыль, какова цена. Решение — за автором проекта: либо делаем рефакторинг отдельным шагом, либо осознанно оставляем костыль с пометкой `TODO(имя, дата)`. Не применять к локальным мелочам внутри самой фичи (приватные хелперы, локальные переменные) — только к изменениям, затрагивающим соседний код, чужие слои, сигнатуры существующих API.

## 14. Масштабируемость (stateless и конкурентность)

Приложение должно запускаться в **N инстансов** без переписывания кода. Количество инстансов — вопрос деплоя, а не архитектуры. Правила, чтобы так и осталось:

### 14.1 Stateless-процесс

- **Никакого состояния в памяти процесса** между запросами. Никаких `GLOBAL_CACHE = {}`, счётчиков, очередей, in-memory-сессий на уровне модуля.
- **Единственное допустимое in-memory-состояние:** чистые кэши (конфиги, скомпилированные regex-ы, константы), загружаемые при старте и больше не меняющиеся.
- **Кэш данных — только Redis.** `functools.lru_cache` — для чистых функций без I/O, не для результатов запросов к БД.
- **Пользовательские сессии — не в памяти.** Сейчас — JWT в HttpOnly-cookie (stateless), со скользящим продлением (`core/middleware/session.py`).
- **Файлы пользователя — не на локальный диск.** Загрузки (изображения, документы) — сразу в S3/MinIO, не в `./uploads/`. Иначе два инстанса не видят загрузки друг друга.

### 14.2 Конкурентный доступ

С N инстансов два запроса могут одновременно делать одно и то же:

- **Уникальность — через `UNIQUE INDEX` в Postgres**, не через `SELECT ... → INSERT`. Ловим `IntegrityError`, конвертируем в доменную ошибку.
- **Фоновые задачи идемпотентны.** Повторный запуск той же задачи не создаёт дублей. Идемпотентный ключ (например, `source_id + content_hash`) или `INSERT ... ON CONFLICT DO NOTHING`.
- **Критические секции — через блокировки БД** (`SELECT ... FOR UPDATE`) или Redis-lock. Не через локальные `threading.Lock` / `asyncio.Lock` — они не работают между процессами.

### 14.3 Готовность к read-репликам

- **Сессия БД — только через DI** (FastAPI `Depends`, аргумент фоновой задачи). Никогда не создавать engine/session внутри роутов, `domain/`, `crud/`.
- Когда понадобится read-реплика — добавим `get_write_session` / `get_read_session`. Код, получающий сессию через DI, не меняется.
- **После `INSERT`/`UPDATE` — читаем результат с мастера**, не с реплики (репликация догоняет). Либо возвращаем данные из самой операции записи.

### 14.4 Что НЕ закладываем заранее

- **Шардирование.** До сотен миллионов строк вопрос решается вертикальным скейлом БД, репликами, кэшем, выносом поиска во внешний движок. YAGNI.
- **Распределённые транзакции (2PC, Saga).** Не нужны, пока данные на одном шарде.
- **Кастомные брокеры, очереди, event sourcing.** Штатная очередь + Redis покрывают всё до серьёзных объёмов.

## 15. Принципы, которым следуем явно

1. **Small Blast Radius.** Каждое изменение локализовано. Рефакторинг — отдельным коммитом от фичи.
2. **Boring Technology.** Не тянем библиотеку, которую использовали один раз. Стандартная библиотека Python > внешняя зависимость.
3. **Least Surprise.** Код ведёт себя так, как подсказывает имя. Функция `get_item` не пишет в БД.
4. **Explicit > Implicit.** Никаких неявных глобальных состояний, «магических» импортов, monkey-patching в рантайме.
5. **One Way To Do It.** Один способ получить сессию БД, один способ рендерить шаблон, один способ логировать.

## 16. Что НЕ делать (красные флаги)

- Копипасту «чтобы не трогать рабочий код».
- Функции `utils.py` / `helpers.py` без внутренней темы — это мусорка.
- Классы-менеджеры на 500 строк (`ItemManager`, `CategoryService` с 20 методами).
- Методы, которые принимают флаг `do_save: bool` и внутри ветвятся — это два метода.
- Глобальные изменяемые переменные модуля (кроме логгера и констант).
- `from module import *`.
- Обход тайпчекера через `# type: ignore` / `# ty: ignore` без указания правила.
- Обход Ruff через `# noqa` без указания правила и причины.
- Закомментированный код. Удалять — git помнит.
- Прямые запросы к БД из роутов или шаблонов.
- Индекс, констрейнт или колонку, созданные `op.*` в миграции и не объявленные в модели (§8.2) — исчезнут при следующем сквоше.
- `alert()` / `confirm()` / `hx-confirm` (§9.3).
- Секреты и персональные данные в логах (§7).

## 17. Когда сомневаешься

1. **SRP** — если функция/класс делает больше одного дела, раздели.
2. **YAGNI** — если фича не нужна сегодня, не пиши её сегодня.
3. **Rule of Three** — дублирование устраняем с третьего повтора, не с первого.
4. **Явное важнее умного.** Предпочитаем понятный код «умному».
5. Если решение неочевидно — открой [docs/DECISIONS/](docs/DECISIONS/) и создай ADR (образец — `0000-template.md`).

## 20. Инфраструктура и эксплуатация

- **Окружения и env-файлы.** `app/core/config.py` читает `.env.template` (база), поверх — `.env.local` (локально) или `.env.docker` (при `ENVIRONMENT=docker`). Вложенные настройки — через `__`: `DB__HOST` → `settings.db.host`. Новая настройка — класс-раздел в `config.py`, ключ во всех трёх файлах с комментарием, зачем он.
- **`.env.docker` лежит в git** вместе с продовыми секретами — репозиторий проекта приватный. CI берёт из него имя образа и копирует файл на сервер.
- **Деплой — пуш в `main`.** CI (`.github/workflows/main.yml`): линт → сборка образов приложения и Postgres → копирование `docker-compose.yml`, `Caddyfile`, `.env.docker` на сервер → `docker compose up -d`. Миграции применяет одноразовый сервис `migrate` до старта `web`.
- **Бэкапы БД** — pgBackRest: WAL непрерывно и полный бэкап раз в сутки в S3, проверка восстановления по воскресеньям, алерт через heartbeat ([docs/guide/ops/backups.md](docs/guide/ops/backups.md), [ADR 0001](docs/DECISIONS/0001-postgres-backups.md)). Ломать `docker/postgres/` — значит ломать базу на проде.
- **Порт Postgres на сервере — только `127.0.0.1`**: Docker правит iptables мимо ufw. Доступ к продовой базе — SSH-туннелем ([docs/guide/ops/dbeaver-prod.md](docs/guide/ops/dbeaver-prod.md)).
- **Лимит запросов — в Caddy** (`Caddyfile`), а не в приложении: своего хранилища для счётчиков (Redis) нет. Появится Redis — лимиты отдельных действий переедут в приложение.
- **Новый сервис в compose** (Redis, Meili, воркер) — с `logging: *default-logging` и без опубликованных наружу портов (`expose`, не `ports`).
