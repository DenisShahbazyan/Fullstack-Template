# ADR 0002. Загрузки в S3: один модуль во всех проектах

Дата: 2026-10-25. Статус: принято.

## Контекст

Файлы пользователей не лежат на диске: приложение работает в нескольких инстансах (CLAUDE.md §6). В SENO и bathhouse загрузки в S3 сделали по-разному: разные клиенты, ключи, превью, доступ, чистка и копия бакета. Поддерживать два решения дороже, а ошибки, найденные в одном, оставались в другом. Каркас должен давать одно решение, которое проекты берут без правок.

## Решение

**Одинаковый во всех проектах модуль загрузок, свой у проекта — только список папок и колонок с ключами.**

- **Бакет у каждого проекта свой — и в проде, и локально.** Чужих файлов в бакете нет, поэтому код не делит его префиксами, а чистка и копия не боятся задеть соседей.
- **Бакет приватный.** В БД хранится ключ (`<папка>/<uuid>.<ext>`), наружу — подписанная на час ссылка (`core/s3/links.py`). Ссылки собираются в роуте до рендера.
- **Фото — через сервер.** Форма шлёт файл приложению, `store_upload` (`core/s3/store.py`) определяет формат по содержимому, перекодирует изображение в WebP (до `IMAGE_MAX_SIDE`, без EXIF) и кладёт рядом превью `<ключ>_thumb.webp`. Документы из `DOCUMENT_TYPES` хранятся как есть. Обработка — в пуле потоков (`core/images.py`), с лимитом в 60 Мп.
- **Временные загрузки для API.** `POST /api/public/v1/files/upload` кладёт файл в `tmp/<id пользователя>/<uuid>.<ext>`. Запись принимает его через `claim_uploads` (`core/s3/claim.py`): только свои ключи, копия в постоянную папку под новым именем. Владелец записан в пути — ни Redis, ни таблицы не нужно.
- **Удаление** — `discard_files` после commit. **Ночная чистка сирот** — сервис `uploads_sweep`: удаляет файлы из `SITE_FOLDERS` и `tmp/` старше `ORPHAN_TTL_HOURS`, на которые не ссылается база (`crud/public/stored_file.py`). Останавливается, если под удаление попало больше половины файлов.
- **Копия бакета** — сервис `uploads_backup` (rclone): раз в сутки зеркалит бакет без `tmp/` в бакет другого провайдера, удалённое хранит 30 дней ([uploads-backups.md](../guide/ops/uploads-backups.md)).
- Проектное: `domain/uploads/project.py` (папки, документы) и `crud/public/stored_file.py` (колонки с ключами). Всё остальное в `core/s3/`, `core/images.py`, `domain/uploads/`, `scripts/uploads/`, `docker/uploads-backup/` правится только в шаблоне и переносится в проекты как есть.

## Отвергнутые варианты

- **Прямая загрузка из браузера для всего.** Изображение всё равно нужно обработать на сервере, а для этого скачать его обратно из S3. Прямая загрузка частями остаётся для того, что через сервер не пропустить (видео в bathhouse), — как проектное дополнение.
- **Публичные объекты.** Проще кэшировать, но открывают всё, что когда-то загрузили: сертификаты, фото непроверенных анкет.
- **Общий бакет с префиксом проекта.** Экономит бакеты, но любой скрипт с ошибкой в префиксе задевает соседей, а чистка и копия должны знать про чужие файлы.
- **Определение типа через libmagic.** Системная зависимость в образе ради десятка сигнатур — `domain/uploads/types.py` делает это сам.

## Последствия

- Новая колонка с ключом файла — строка в `KEY_COLUMNS`, новая папка — в `SITE_FOLDERS`. Забыть первое — чистка удалит живые файлы; это записано в скилле `uploads`.
- Подписанная ссылка меняется при каждом рендере, поэтому браузер не кэширует картинки между заходами. Если станет заметно — подписывать с округлённым временем.
- Новый проект сразу получает `uploads_backup` и `uploads_sweep`. Пока бакет пуст, копия считает это сбоем и шлёт `/fail`: включать её стоит, когда появились файлы.
