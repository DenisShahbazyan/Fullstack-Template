# Копия загрузок (S3)

Загрузки сайта лежат в своём бакете S3 (раздел `S3__*`). Раз в сутки [rclone](https://rclone.org/) копирует этот бакет в бакет **другого провайдера**. Так загрузки переживут и ошибочное удаление, и потерю аккаунта у провайдера основного бакета. Как устроены сами загрузки — [ADR 0002](../../DECISIONS/0002-s3-uploads.md).

## Как устроено

| Что | Где |
| --- | --- |
| Образ с rclone | [docker/uploads-backup/Dockerfile](../../../docker/uploads-backup/Dockerfile), собирается в CI как `<DOCKER_USERNAME>/<DOCKER_IMAGE_NAME>-uploads-backup:latest` |
| Расписание и логика | [uploads-backup-scheduler](../../../docker/uploads-backup/bin/uploads-backup-scheduler) |
| Сервис | `uploads_backup` в [docker-compose.yml](../../../docker-compose.yml) |
| Ключи копии | раздел `UPLOADS BACKUP` в [.env.docker](../../../.env.docker) |

Структура бакета с копией:

```
current/          зеркало загрузок на момент последнего запуска
archive/<дата>/   файлы, которые в этот день пропали или изменились в источнике
state/            отметка последнего успешного запуска
```

Что делает сервис раз в сутки (UTC), если сегодня успешной копии ещё нет:

1. Проверяет, что бакет загрузок не пуст. Пустой или недоступный источник сбой, а не повод стереть копию.
2. `rclone sync` приводит `current/` в соответствие с источником. Всё, что при этом удаляется или перезаписывается, переезжает в `archive/<сегодня>/`. Больше 5000 удалений за раз (`--max-delete`) — сбой: тысячи сразу значат баг чистки или чужой ключ, а не обычные сутки. Новые файлы при этом всё равно копируются.
3. `rclone check` убеждается, что каждый файл источника есть в копии с тем же размером. Файлы моложе 10 минут не проверяются: они могли появиться уже после синхронизации.
4. Удаляет из `archive/` каталоги старше 30 дней.
5. Записывает отметку успеха и шлёт «успех» на heartbeat. Если любой шаг упал, шлёт `/fail` и повторяет через час.

Папка `tmp/` (временные загрузки) не копируется. Запись, принимая файл из `tmp/`, копирует его в постоянную папку (`app/core/s3/claim.py`), а брошенное в `tmp/` удаляет чистка сирот через сутки.

Чистка сирот (сервис `uploads_sweep`, 04:30 UTC) удаляет файлы папок сайта, на которые не ссылается база. Она идёт после суточной копии, поэтому удалённое ещё 30 дней лежит в `archive/`. Если сегодняшней копии нет (получатель недоступен), чистка пропускает сутки: отметку копии `uploads_backup` кладёт в общий том `uploads_backup_state`, `uploads_sweep` читает её только на чтение. Ключ к бакету копии сайту для этого не нужен.

Перезапуск при деплое копию не повторяет: отметку «сегодня уже было» сервис берёт из самого бакета.

## Включение

На сервере ничего делать не нужно.

1. У другого провайдера (Selectel, Yandex Object Storage, Backblaze B2 и т.п.) создайте **приватный бакет** и **ключ доступа только к нему**.
2. Включите в бакете шифрование на стороне провайдера, если он это умеет: в загрузках бывают персональные данные.
3. Заполните раздел `UPLOADS BACKUP` в `.env.docker`: `UPLOADS_BACKUP_BUCKET`, `RCLONE_CONFIG_DST_ENDPOINT`, `RCLONE_CONFIG_DST_REGION`, ключ и секрет.
4. Для алертов (необязательно: без адреса копия идёт так же, но о сбое никто не узнает) в Better Stack заведите **отдельный** heartbeat с периодом 1 день и запасом 2 часа, адрес впишите в `UPLOADS_BACKUP_PING_URL`. Общий с бэкапом БД не подойдёт: успех одного скрыл бы сбой другого.
5. Запушьте в основную ветку. После деплоя `uploads_backup` сразу сделает первую копию. Первый запуск долгий: он переносит весь бакет.

Проверка:

```sh
sudo docker logs uploads_backup     # без ошибок, в конце «Checks» и «0 differences found»
```

Пока `UPLOADS_BACKUP_BUCKET` пустой, сервис пишет «копия загрузок выключена» и ничего не делает. Включайте копию, когда в бакете уже есть файлы: пустой источник она считает сбоем и шлёт `/fail`.

## Смена хранилища

Копию можно в любой момент направить в другой бакет или к другому провайдеру: поменяйте `UPLOADS_BACKUP_BUCKET` и `RCLONE_CONFIG_DST_*` в `.env.docker` и задеплойте.

- `uploads_backup` не находит в новом бакете отметки о копии и сразу переносит туда весь бакет загрузок. Первый запуск долгий.
- **История удалённого начинается заново**: `archive/` с файлами, удалёнными за последние 30 дней, остаётся в старом бакете. Не удаляйте его 30 суток.
- Старый бакет никто не чистит: удалите его сами, когда он перестанет быть нужен.

## Повседневное

Команды выполняются внутри контейнера, ключи берутся из его окружения.

```sh
# Что лежит в копии и сколько весит
sudo docker exec uploads_backup rclone size dst:$UPLOADS_BACKUP_BUCKET/current

# Дни, за которые в архиве есть удалённые или изменённые файлы
sudo docker exec uploads_backup sh -c 'rclone lsf --dirs-only dst:$UPLOADS_BACKUP_BUCKET/archive'

# Последний успешный запуск
sudo docker exec uploads_backup sh -c 'rclone cat dst:$UPLOADS_BACKUP_BUCKET/state/last-success'

# Копия вне расписания: удалить отметку, сервис подхватит в течение минуты
sudo docker exec uploads_backup sh -c 'rclone deletefile dst:$UPLOADS_BACKUP_BUCKET/state/last-success'
```

## Восстановление

Порядок: **сначала база, потом файлы.** Лишний файл в бакете безвреден, его подберёт чистка сирот, а ссылка на несуществующий файл ломает страницу.

**Вернуть один удалённый файл** (путь известен из БД или из лога):

```sh
sudo docker exec uploads_backup sh -c '
  rclone ls dst:$UPLOADS_BACKUP_BUCKET/archive --include "photos/abc.webp"
  rclone copyto dst:$UPLOADS_BACKUP_BUCKET/archive/2026-10-17/photos/abc.webp src:$UPLOADS_BACKUP_SOURCE_BUCKET/photos/abc.webp'
```

**Вернуть всё после потери бакета.** Создайте новый бакет, пропишите его в `S3__*` и скопируйте в него `current/`:

```sh
sudo docker exec uploads_backup sh -c '
  rclone copy dst:$UPLOADS_BACKUP_BUCKET/current src:$UPLOADS_BACKUP_SOURCE_BUCKET --transfers 8 -v'
```

Если пропажу заметили после очередной синхронизации, файлы удалённого дня лежат в `archive/<дата>/`. Верните их `rclone copy` из этого каталога поверх `current/`.

## Разное

- **Сроки.** Удалённый или перезаписанный файл остаётся в `archive/` 30 суток, срок задан `RETENTION_DAYS` в скрипте. Файл, который существует в источнике, лежит в `current/` без ограничения.
- **Если источник опустел** (ошибочно удалили бакет или ключ потерял права), синхронизация перенесёт все файлы в `archive/<сегодня>/`, и вернуть их можно в течение 30 суток. Сам по себе пустой бакет `sync` не запустит: сработает проверка из шага 1 и придёт алерт.
- **Законная массовая чистка** (удалили раздел с тысячами фото) упрётся в потолок удалений, и каждый час будет приходить `/fail`. Убедившись, что удаление настоящее, впишите `UPLOADS_BACKUP_MAX_DELETE` побольше в `.env.docker`, задеплойте, после успешной копии верните пустое значение.
- **Трафик.** Данные идут через сервер: из основного S3 на сервер и дальше к другому провайдеру. После первого запуска переносятся только новые файлы.
- **Ключ источника.** Сервис читает бакет загрузок тем же ключом, что и сайт. Записей в источник он не делает.
